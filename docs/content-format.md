# Формат контента

> Утверждено 2026-10-20 (объединены `docs/drafts/content-format.md` и стандарт из `content/_plan/01-standard.md`).

## 1. Контекст: backend интернет-магазина
Во всех курсах направления Backend задачи взяты из работы backend-разработчика интернет-магазина: «менеджер просит выгрузку», «тимлид просит исправить», «упал сервер». Абстрактных примеров (`foo/bar`, котики, `a = 5`) нет.

**Магазин — предметная область, а не собираемый проект.** Каждая тема и задача самостоятельна, итоговой версии магазина нет.

- Сущности и поля берём только из [shop-schema.md](shop-schema.md). Нужно новое поле — сначала меняем схему.
- В Python товар — `dict` или класс с ключами из таблицы `products`; в Linux лог — запросы к страницам этих товаров и т. д.
- Деньги — `Decimal` (Python) и `numeric` (SQL), никогда не `float`.

**Таблица 1.** Чем ученик занят в каждом курсе.

| Шаг | Курс | Чем занят ученик | С чем работает |
|---|---|---|---|
| 10 | Python | пишет бизнес-логику магазина | товары, корзина, заказы: структуры Python → классы → async |
| 15 | Python под капотом | разбирается, почему код магазина ведёт себя странно | те же сущности; потерянные ключи, ловушки ссылок, утечки |
| 20 | Linux | работает на сервере магазина | `/srv/shop` (код), `/var/log/shop` (логи), `/etc/nginx` |
| 30 | Git | ведёт репозиторий магазина | фича «промокоды», ветки, конфликты, PR |
| 35 | Веб и HTTP | разбирается, как сайт и покупатель общаются по HTTP | запросы к API магазина |
| 40 | SQL | работает с БД магазина напрямую | учебная БД «магазин» |
| 50 | Django | делает сайт магазина; ORM — для нужд страниц | приложение `shop` |
| 70 | Docker | упаковывает магазин в контейнеры | Django + Postgres + Nginx в compose |
| 80 | Nginx и деплой | выводит магазин в продакшен | Gunicorn, статика, HTTPS, CI/CD |

## 2. Читатель и сложность
- **Читатель** — новичок в теме, но не в компьютерах: знает, что такое сайт, сервер, форма, URL, умеет гуглить. Термины не разжёвываем. Но и не усложняем: в базовых курсах — только то, что нужно на этом шаге; «как устроено» — в блок «Глубже» и в «Python под капотом».
- **Разделы** курса имеют уровень ●○○ основы → ●●○ применение → ●●● продвинутое и идут от простого к сложному.
- **Без пробелов:** тема опирается только на пройденное — выше в своём курсе или в курсах с меньшим шагом.
- Первые разделы — уроки на 5–8 минут; последние — до 13 минут.

## 3. Структура папок
```
content/
  backend/                          # направление
    _track.yaml                     # title, description, order
    _shared/schema.sql              # учебная БД «магазин»
    python/                         # курс
      _course.yaml                  # title, description, engine, order (шаг 10)
      01-first-steps/               # раздел: NN-slug
        _section.yaml               # title, level (1–3)
        02-variables-and-types/     # тема: NN-slug
          _topic.yaml               # title
          01-variables-and-types.md # урок
          02-form-quantity.yaml     # задачи
          img/names-to-values.svg   # рисунки урока
  _plan/                            # программы курсов (рабочие документы)
  _tools/check_tasks.py             # проверка эталонов задач
```
`NN` задаёт порядок. Slug — латиница, kebab-case; после публикации не меняется (от него зависят URL и прогресс).

`_course.yaml` → `engine`: `python`, `sql`, `django`, `linux` или пусто (курс без тренажёра — только задачи `quiz`/`fix`).

## 4. Урок
**Тема = 1 урок + 2–5 задач.** Урок — Markdown с front matter:
```yaml
---
title: Переменные и типы данных
type: lesson
level: 1            # уровень раздела
reading_time: 8     # минуты
---
```

**Заголовки H2 одинаковые во всех уроках**, чтобы читатель знал, какой блок его ждёт:

**Таблица 2.** Блоки урока по порядку.

| Заголовок | Что в блоке |
|---|---|
| `## Теория` | 1–2 абзаца: что это, зачем, главная идея; кода нет или почти нет |
| `## Наглядно` | вся тема одним взглядом: таблица и/или рисунок |
| `## На практике` | одна рабочая ситуация из магазина и разбор по шагам: `### Шаг 1. <глагол…>` |
| `## Частые ошибки` | ошибка → почему → как правильно |
| `## Итог` | подробный конспект: 6–10 пунктов в смысловых группах (`**Группа**` + список) с мини-примерами |
| `## Вопросы на собеседовании` | 3–5 вопросов, ответы в `<details>` |
| `## Глубже` | только в базовом Python и только если есть связанная тема в «Python под капотом» |
| `## Связанные темы` | в «Python под капотом»: ссылка обратно на базу |

**Подписи — у каждого блока:**
- таблица: `**Таблица N.** Что в таблице и зачем.`;
- рисунок: `**Рисунок N.** Что показывает, на что смотреть.`;
- код: одно предложение перед ним, заканчивается двоеточием;
- вывод программы: перед ним «Результат:».

Нумерация таблиц и рисунков — сквозная в пределах урока.

**Рисунки:**
- только SVG в `img/` рядом с уроком: `![Рисунок 1. …](img/<имя>.svg)`; псевдографика в Markdown запрещена;
- цвета — переменные темы сайта с запасным цветом светлой темы: `fill:#ffffff;fill:var(--surface,#ffffff)`; шрифты — `var(--font-main)`, `var(--font-code)`;
- в `<title>` — описание рисунка; ширина до 900 px; текст не мельче 12 px;
- сайт вставляет SVG в страницу inline — тогда рисунок меняет цвета вместе с темой. Поэтому стили рисунка не должны задевать страницу: все классы — с префиксом `fig-`, корневой `<svg>` — класс `fig`, общие селекторы — только внутри `.fig`. `id` внутри SVG загрузчик делает уникальными сам;
- рисунки рисуются кодом: стиль и примитивы — `content/_tools/svgkit.py`, все рисунки — `content/_tools/figures.py` (`python3 content/_tools/figures.py` пересобирает файлы). Вручную SVG не правим.

**Правила текста:** начинаем с «зачем»; каждое понятие — на примере с результатом; сравнения — таблицей; актуальные версии (Python 3.12, PostgreSQL 16, Django 5.x); весь код реально запускается.

## 5. Задачи
**Задачи — подводные камни, а не тренировка.** Тренируется ученик сам, в песочнице. Каждая задача ловит **один подводный камень** — то, что легко упустить и на чём ошибаются в работе и на собеседовании. Задачи не повторяют примеры урока; если задачу нельзя сформулировать через подводный камень, её не делаем.

- 2–5 задач на тему, у каждой `pitfall` — одна фраза: какой камень ловит.
- `difficulty`: 1 — лёгкая, 2 — средняя, 3 — сложная.
- 1–3 подсказки (`hints`): от намёка к почти готовому решению.
- `explanation` объясняет, почему решение работает, а не пересказывает код.

**Таблица 3.** Типы задач.

| Тип | Где | Проверка |
|---|---|---|
| `exercise` | базовые курсы | тесты; у каждого теста своё сообщение `fail` — подсказка, какой камень не учтён |
| `predict` | «Python под капотом» | тренажёр запускает `code` и сравнивает вывод с ответом ученика |
| `quiz` | темы без живого запуска | выбор одного или нескольких ответов, расстановка шагов по порядку |
| `fix` | конфиги и код без движка | найти и исправить ошибку в файлах; проверка по правилам (регулярные выражения) |

### exercise (Python)
```yaml
title: Тарифы доставки
type: exercise
difficulty: 2
pitfall: В цепочке elif срабатывает первая подходящая ветка — порядок важен.
statement: |
  Условие. Что дано, что нужно получить (имена переменных, формат вывода).
inputs: |               # необязательно: входные данные задачи — код Python
  total = 2500
starter_code: |
  ...
check:
  type: tests
  tests:
    - code: assert run(total=500)["delivery"] == 399
      fail: Сообщение-подсказка, если тест не прошёл.
solution: |
  ...
hints: [...]
explanation: |
  ...
```

**Как выполняются тесты:**
1. Сначала выполняется `inputs` — короткий код, задающий входные данные (`total = 2500`, `price = Decimal("999")`), затем код ученика в том же пространстве имён. Код ученика **не присваивает** входные переменные — их значения приходят снаружи (в песочнице ученик видит `inputs` как блок «Входные данные»).
2. Тесты выполняются в пространстве имён этого запуска. Кроме переменных ученика им доступны:
   - `output` — всё, что программа вывела в stdout;
   - `source` — текст кода ученика;
   - `run(**значения)` — запустить код ученика заново: выполняется `inputs`, переданные значения подменяют входные (`run(total=500)`), затем код ученика. Возвращает пространство имён, где есть и `output`.
3. Тайм-аут выполнения — 2 секунды: бесконечный цикл засчитывается как непройденный тест с сообщением «Программа не завершилась».

Тесты по возможности проверяют несколько входных данных через `run()` — так нельзя «подогнать» ответ под один случай.

### exercise (SQL)
```yaml
title: Покупатели без заказов
type: exercise
difficulty: 2
pitfall: INNER JOIN отбрасывает строки без пары.
statement: |
  Выведите `id` и `email` пользователей без заказов. Отсортируйте по `id`.
solution: |
  SELECT u.id, u.email
  FROM users u
  LEFT JOIN orders o ON o.user_id = u.id
  WHERE o.id IS NULL
  ORDER BY u.id;
check:
  type: result           # result — сравнить результат; state — сравнить таблицы после DML
  order_matters: true
hints: [...]
explanation: |
  ...
```
В условии всегда сказано, какие колонки и в каком порядке вывести и нужна ли сортировка — чтобы проверка была однозначной.

Формат многофайловых задач (Django: `models.py`, `views.py`, `urls.py`, шаблон) — ⏳ на этапе 5 разработки, вместе с тренажёром Django.

### quiz
```yaml
title: Код ответа «товар закончился»
type: quiz
kind: single             # single — один ответ, multiple — несколько, order — расставить по порядку
difficulty: 1
pitfall: 404 — «нет такого ресурса», а не «действие невозможно в текущем состоянии».
statement: |
  Покупатель оформляет заказ, а товар только что закончился. Какой код ответа вернуть из API?
options:
  - 200 OK
  - 404 Not Found
  - 409 Conflict
  - 500 Internal Server Error
answer: [2]              # индексы options с нуля
explanation: |
  ...
```
- `single` — в `answer` ровно один индекс; `multiple` — один или больше, ученик должен отметить все и только их;
- `order` — `answer` содержит **все** индексы `options` в правильном порядке; в YAML варианты можно писать в любом порядке, на сайте они перемешиваются;
- `hints` — как у `exercise`, по желанию.

### fix
```yaml
title: Фото товара не загружается
type: fix
difficulty: 2
pitfall: Nginx по умолчанию принимает тело запроса до 1 МБ — больше даёт 413.
statement: |
  Менеджер загружает фото товара на 5 МБ и получает «413 Request Entity Too Large».
  Исправьте конфиг так, чтобы принимались файлы до 10 МБ.
files:                   # файлы, которые видит и правит ученик: имя → исходный текст
  nginx.conf: |
    server {
        listen 80;
        location / {
            proxy_pass http://web:8000;
        }
    }
check:
  type: rules
  rules:
    - must_match: '^\s*client_max_body_size\s+10[mM];'
      fail: Ограничение на размер тела запроса задаётся директивой client_max_body_size.
    - must_not_match: '^\s*client_max_body_size\s+0;'
      fail: "0 снимает ограничение совсем — так любой может загрузить файл любого размера."
solution:                # исправленные файлы: эталон для проверки правил и показа после решения
  nginx.conf: |
    server {
        listen 80;
        client_max_body_size 10m;
        location / {
            proxy_pass http://web:8000;
        }
    }
hints: [...]
explanation: |
  ...
```
- правило — `must_match` (шаблон обязан найтись) или `must_not_match` (не должен найтись) + `fail`;
- `file:` в правиле — какой файл проверять; можно не писать, если файл один;
- шаблон ищется в любом месте файла, `^` и `$` — границы строк. Пишем регулярные выражения, одинаково работающие в Python и JavaScript: без `(?P<имя>)`, без флагов внутри шаблона, без `\A`/`\Z`;
- шаблон директивы или строки кода начинаем с `^\s*` — иначе засчитается и закомментированная строка (`# client_max_body_size 10m;`);
- правила проверяют смысл, а не форму: допускают лишние пробелы (`\s+`), разный регистр единиц (`[mM]`), любое место директивы в файле.

### Проверка эталонов
`python3 content/_tools/check_tasks.py` проверяет задачи:
- `exercise` (Python): эталон (`solution`) проходит все тесты, `starter_code` хотя бы один не проходит;
- `predict`: ответ совпадает с реальным выводом;
- `quiz`: индексы `answer` существуют и соответствуют `kind`;
- `fix`: все шаблоны компилируются, `solution` проходит все правила, исходные `files` хотя бы одно не проходят, а `solution`, в котором исправленные строки закомментированы, правила **не** проходит.

Запускать перед каждым коммитом контента.

## 6. Связь базового Python и «Python под капотом»
Урок базы заканчивается блоком «Глубже» (1–2 предложения + ссылка на тему «Под капотом»), если связанная тема есть. Урок «Под капотом» заканчивается «Связанными темами» со ссылкой на базу.
